# Разработка RustText с LLM-агентами

Владелец задаёт цель и ограничения, агент реализует изменение, собирает подтверждения и открывает PR на GitHub. Единица работы — задача с наблюдаемым результатом, отдельный worktree и одна ветка. Где искать код и обязательные правила, указано в [AGENTS.md](../AGENTS.md).

## Начало задачи

1. Определи ожидаемый результат и способ увидеть его. Сверь задачу с открытыми issues и PR по [правилам ниже](#связь-pr-с-issues). Для сложного изменения запиши затронутые данные, совместимость, риск сбоя и проверки. Зафиксируй решения, которые понадобятся в следующей задаче, рядом с кодом.
2. Проверь, существует ли worktree этой задачи, через `git worktree list`. Продолжай в нём, если он относится к нужной ветке. Сверь `git rev-parse --show-toplevel`, `git status --short --branch` и `git diff`. Учти отдельно staged diff через `git diff --cached`.
3. Для новой задачи обнови `origin/main` через `git fetch origin`. В Codex создай worktree от обновлённой `origin/main`. Если получился detached HEAD, выполни `git switch -c codex/<задача>` в новом worktree. Для обычного Git из исходного checkout:

~~~powershell
git fetch origin
git worktree add -b codex/fix-log-navigation ../RustText-fix-log-navigation origin/main
Set-Location ../RustText-fix-log-navigation
git status --short --branch
~~~

После ошибки команды выясни причину до следующего шага. При занятом имени подключись к worktree нужной задачи или выбери новое имя. Если базовую ветку надо обновить в уже опубликованной задаче, слей свежую `origin/main` в рабочую ветку и повтори проверки. При конфликте разберись с обеими версиями и сохрани смысл изменений. [Git worktree](https://git-scm.com/docs/git-worktree) · [Worktrees в Codex](https://learn.chatgpt.com/docs/environments/git-worktrees)

## Связь PR с issues

В начале работы просмотри [открытые issues](https://github.com/Illson/RustText/issues?q=is%3Aissue%20is%3Aopen) и проверь [открытые PR](https://github.com/Illson/RustText/pulls?q=is%3Apr%20is%3Aopen) по теме. Если issue уже есть, прочитай её описание и обсуждение, сверь критерии приёмки и учти изменения, которые уже предлагаются. Если от трактовки критерия зависит закрытие issue, согласуй его с владельцем проекта.

При создании PR заполни `## Цель` и `## Связь с issues`. Сформулируй ожидаемый результат и границы работы. При изменении объёма работы обнови описание.

- **Issue решена полностью.** В готовом PR в `main` добавь отдельную строку `Closes #N` для каждой открытой issue, все критерии которой выполнены и проверены. В `## Проверки` укажи, каким тестом или ручным сценарием подтверждён каждый критерий или группа критериев. Пример — [PR #29](https://github.com/Illson/RustText/pull/29).
- **Работа частичная, смежная или ещё требует проверки.** Напиши `Связано с #N` и укажи, что покрывает PR и что ещё нужно сделать или проверить. В черновике укажи, планируешь ли закрыть issue этим PR. Для такой связи используй обычное упоминание в тексте. Ключевые слова закрытия в описании PR или коммите и ручная привязка через `Development` предназначены для закрытия issue.
- **Связанной issue нет.** Укажи это в описании PR.

Строка `Closes #N` сообщает о намерении закрыть issue. GitHub закроет её после слияния PR в `main`. Оставляй issue открытой до слияния. Если из PR убрали часть решения или проверка выявила невыполненный критерий, замени `Closes #N` на `Связано с #N` и обнови список оставшейся работы. [Связывание PR с issue на GitHub](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

## Реализация и проверка

- Меняй код небольшими частями. Для регрессии воспроизведи исходное поведение, добавь тест на наблюдаемый результат и проверь, что тест ловит дефект. Для миграций, файловых операций и обновлений проверь совместимость, отмену, повторный запуск и частичный сбой, если эти сценарии затронуты.
- Для проекта используй команды из [README](../README.md#проверка) на Windows x64 MSVC. Во время разработки запусти `tools/Check.ps1 -Mode Targeted -TestFilter '<модуль>::'`. Перед доставкой законченного изменения Rust выполни `tools/Check.ps1 -Mode Full`: форматирование, все тесты и Clippy выполняются последовательно. Не повторяй полный прогон без новых изменений или неразобранного сбоя. Для чисто текстовых правок локально проверь diff, смысл, ссылки, пути и команды.
- Локальный `tools/Check.ps1` ограничивает работу двумя логическими CPU, двумя процессами Cargo и приоритетом BelowNormal; дочерние процессы Windows наследуют маску CPU. Для сборки приложения выбери режим `Build` или `Release`. Не очищай `target` без установленной причины. Для последовательных проверок в нескольких worktree передай один абсолютный `-CacheDirectory`, сохраняя версию Rust и флаги. [Cargo](https://doc.rust-lang.org/cargo/reference/config.html) · [Наследование маски CPU](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setprocessaffinitymask)
- Запускай приложение из текущего worktree с отдельным `LOCALAPPDATA`, чтобы рабочий RustText не перехватил запуск и тест не затронул настоящую сессию. Для ручной проверки используй временные файлы. Пример из корня worktree:

~~~powershell
$previousLocalAppData = $env:LOCALAPPDATA
$profile = Join-Path $PWD.Path ("target/qa-profile/" + [guid]::NewGuid())
New-Item -ItemType Directory -Path $profile -Force | Out-Null
try {
    $env:LOCALAPPDATA = $profile
    cargo run --locked
} finally {
    $env:LOCALAPPDATA = $previousLocalAppData
}
~~~

Открой нужный сценарий и закрой тестовый RustText перед возвратом к текущему терминалу. Для больших логов используй синтетические фикстуры и методику из [отчёта проверки](verification.md). Изменения упаковки тестируй через `tools/Package-RustText.ps1` и архив из `target`. Для обновления используй тестовые архивы и данные выпуска, проверяй ветки отказа и восстановления.

`Cargo.lock` хранится в Git. Обновляй его через Cargo при целенаправленном изменении зависимостей. Для нового crate проверь необходимость, лицензию, происхождение и известные уязвимости. Для изменения графа зависимостей используй RustSec при доступном `cargo audit`, а при отсутствии инструмента укажи, как проверял зависимости. [Cargo.lock](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html) · [Cargo test](https://doc.rust-lang.org/cargo/commands/cargo-test.html) · [Clippy](https://doc.rust-lang.org/clippy/usage.html) · [RustSec](https://rustsec.org/)

## Коммит, push и проверка на GitHub

1. Проверь `git diff --check`. Добавь только файлы задачи через `git add -- <файлы>`. Проверь `git diff --cached --check` и прочитай `git diff --cached` целиком. Убедись, что в коммит попадают нужные новые файлы и что нет токенов, профилей, пользовательских логов или сборочных артефактов.
2. Сделай коммит, который можно понять по сообщению и проверить отдельно. Если владелец поручил оставить работу локально, заверши её после локального коммита и проверок. Перед push сверь адрес `origin`, имя ветки и `git log --oneline origin/main..HEAD`. Публикуй свою ветку обычным push:

~~~powershell
$branch = git branch --show-current
if ($LASTEXITCODE -ne 0 -or $branch -notlike 'codex/*') {
    throw 'Нужна рабочая ветка codex/*'
}
git push --set-upstream origin "HEAD:refs/heads/$branch"
if ($LASTEXITCODE -ne 0) {
    throw 'GitHub не принял push'
}
$head = git rev-parse HEAD
$published = git ls-remote --exit-code origin "refs/heads/$branch"
if ($LASTEXITCODE -ne 0 -or ($published -split '\s+')[0] -ne $head) {
    throw 'GitHub не подтвердил ожидаемый коммит'
}
~~~

При отказе non-fast-forward посмотри, кто и что добавил в ветку. Согласуй чужие изменения перед обновлением своей работы. Прямой push в `main` и перезапись опубликованной истории исключены из обычного процесса. [Git push](https://git-scm.com/docs/git-push)

3. После подтверждения SHA открой PR из рабочей ветки в `main` или обнови существующий PR этой ветки. Для незавершённого изменения используй черновик. С установленным GitHub CLI открой PR через `gh pr create --base main --head $branch --title "Описание изменения" --body-file <файл>`. Без GitHub CLI используй подключение к GitHub или страницу сравнения веток. [GitHub CLI](https://cli.github.com/manual/gh_pr_create)
4. В PR добавь разделы `## Цель`, `## Связь с issues`, `## Изменения` и `## Проверки`. Опиши наблюдаемое изменение, выполненные команды и результаты, ручные сценарии, пропущенные проверки и риски. Используй [правила связи PR с issues](#связь-pr-с-issues). Дождись проверок через `gh pr checks --watch` или [GitHub Actions](https://github.com/Illson/RustText/actions). Проверь, что результаты относятся к текущему коммиту PR. Ошибку разбери по логу и исправь в этой же ветке. При недоступности GitHub или внешнего окружения укажи конкретный блокер. [Проверки PR](https://cli.github.com/manual/gh_pr_checks)
5. Оставь worktree доступным, пока задача открыта или нужна для проверки. Когда он больше не нужен, проверь чистоту дерева и сохранность коммитов. Для worktree в Codex используй архивирование, для обычного Git — `git worktree remove <путь>` из другого checkout.

## Ревью PR

1. Сверь базовую ветку и текущий SHA PR. Прочитай цель, связанные issues, критерии, проверки и существующие обсуждения. Посмотри весь diff в контексте кода. Для `Closes #N` проверь, чем подтверждено полное выполнение issue. Если критерий остался открытым, попроси в ревью указать частичную связь.
2. Открой `Files changed` и привяжи каждое подтверждённое замечание к подходящей строке или диапазону diff. Начни с приоритета и конкретного действия. Формат `[P2]` показан в [замечании в PR #7](https://github.com/Illson/RustText/pull/7#discussion_r4591377163). Опиши условие проявления, последствие и ожидаемое поведение. Приложи короткое воспроизведение, упавшую проверку или объясни, как проблема следует из кода. Замечание без подходящей строки, например о непокрытом критерии issue, оставь в итоговом тексте ревью.
3. Перед публикацией сверь SHA PR. Если он изменился, проверь новый коммит. Отправь замечания одним GitHub Review с решением `Comment`, как в [PR #7](https://github.com/Illson/RustText/pull/7). В итоге укажи проверенный SHA, охват, выполненные проверки и их результаты, существенные ограничения и замечания, которые мешают слиянию. Если замечаний нет, так и напиши. Проверь, что ревью опубликовано в PR. [Как отправить ревью на GitHub](https://docs.github.com/en/pull-requests/get-started/reviewing-pull-requests-quickstart)
4. Автор отвечает в существующих тредах и указывает коммит с исправлением и результат проверки. При повторном ревью проверь исправление на новом SHA и ответь в исходном треде. Для новых дефектов открывай отдельные треды. Пример повторного ревью — [PR #6](https://github.com/Illson/RustText/pull/6).

## Что обеспечивает CI

[Windows CI](../.github/workflows/windows-ci.yml) запускает форматирование, тесты и Clippy на Windows x64 при push в `main`, в ветки `codex/**` и для PR в `main`. CI устанавливает точную версию Rust 1.100.0 из README и использует `--locked` для сборки тестов и проверки Clippy. Версию Rust обновляй вместе с проверкой на Windows и документацией. [Образ Windows](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md) · [Rust 1.100.0](https://github.com/rust-lang/rust/releases/tag/1.100.0)

CI имеет разрешение `contents: read` и использует action, закреплённый по полному SHA. Сборки PR запускаются через `pull_request` без передачи секретов в команды. Для обязательной проверки перед слиянием владелец может указать `Windows Rust checks` в правилах `main` после первого появления результата. Изменение правил ветки и выпуск новой версии выполняются отдельными задачами. [Безопасность GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use) · [Правила PR](https://docs.github.com/en/pull-requests/reference/managing-and-standardizing-pull-requests)

Когда агент повторяет ошибку, добавь недостающее воспроизведение, тест, проверку CI или короткое объяснение рядом с кодом. Если задачи постоянно требуют ручного переноса контекста, перенеси воспроизводимые инструкции в репозиторий. [Опыт OpenAI с разработкой агентами](https://openai.com/index/harness-engineering/)
