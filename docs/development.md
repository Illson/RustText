# Разработка RustText с LLM-агентами

Владелец задаёт цель и ограничения, агент реализует изменение, собирает подтверждения и открывает PR на GitHub. Единица работы — задача с наблюдаемым результатом, отдельный worktree и одна ветка. Где искать код и обязательные правила, указано в [AGENTS.md](../AGENTS.md).

## Начало задачи

1. Определи ожидаемый результат и способ увидеть его. Сверь задачу с открытыми issues и PR по [правилам ниже](#связь-pr-с-issues). Для сложного изменения запиши затронутые данные, совместимость, риск сбоя и проверки. Зафиксируй решения, которые понадобятся в следующей задаче, рядом с кодом.
2. Проверь, существует ли worktree этой задачи, через `git worktree list`. Продолжай в нём, если он относится к нужной ветке. Сверь `git rev-parse --show-toplevel`, `git status --short --branch` и `git diff`. Учти отдельно staged diff через `git diff --cached`.
3. Для новой задачи обнови `origin/main` через `git fetch origin`. В Codex создай worktree от обновлённой `origin/main`. Если получился detached HEAD, выполни `git switch -c codex/<задача>` в новом worktree. Для обычного Git из исходного checkout:

~~~powershell
git fetch origin
git worktree add -b codex/fix-log-navigation ../RustText-fix-log-navigation origin/main
Set-Location ../RustText-fix-log-navigation
git status --short --branch
~~~

После ошибки команды выясни причину до следующего шага. При занятом имени подключись к worktree нужной задачи или выбери новое имя. Если базовую ветку надо обновить в уже опубликованной задаче, слей свежую `origin/main` в рабочую ветку и повтори проверки. При конфликте разберись с обеими версиями и сохрани смысл изменений. [Git worktree](https://git-scm.com/docs/git-worktree) · [Worktrees в Codex](https://learn.chatgpt.com/docs/environments/git-worktrees)

## Связь PR с issues

В начале работы просмотри [открытые issues](https://github.com/Illson/RustText/issues?q=is%3Aissue%20is%3Aopen) и проверь [открытые PR](https://github.com/Illson/RustText/pulls?q=is%3Apr%20is%3Aopen) по теме. Если issue уже есть, прочитай её описание и обсуждение, сверь критерии приёмки и учти изменения, которые уже предлагаются. Если от трактовки критерия зависит закрытие issue, согласуй его с владельцем проекта.

Если берёшь issue в работу на GitHub, обозначь, за какую часть отвечаешь и планируешь ли закрыть её целиком. Пока PR нет, оставь короткий комментарий в issue. В описании PR укажи, какую часть issue он покрывает. Обновляй описание, если объём работы изменился. При поручении работать локально зафиксируй намерение в отчёте.

- **Issue решена полностью.** В готовом PR в `main` добавь отдельную строку `Closes #N` для каждой решённой issue. В разделе «Проверки» свяжи каждый критерий приёмки с результатом теста или ручного сценария. В [PR #29](https://github.com/Illson/RustText/pull/29) автор указал, как проверил поиск и активацию окон.
- **Работа частичная, смежная или ещё требует проверки.** Укажи `Связано с #N`, результат этого PR и оставшуюся работу. В черновике можно написать, например, «Связано с #N. Поиск по PID готов. Планирую закрыть задачу этим PR после проверки восстановления свёрнутого окна».
- **Связанной issue нет.** Укажи это в описании PR.

Оставляй issue открытой до слияния. Строка `Closes #N` в описании PR закроет issue при слиянии в `main`. В сообщениях коммитов ссылайся на issue по номеру. Если объём сократился, замени `Closes #N` на `Связано с #N` и перечисли оставшиеся критерии. Проверь также ручную привязку в `Development` и сообщения коммитов. Удали лишнюю ручную привязку. Если в опубликованном коммите есть закрывающее слово для этой issue, предупреди об этом в PR. Такой коммит тоже закроет issue при попадании в `main`. При squash убери закрывающее слово из итогового сообщения. [Связывание PR с issue на GitHub](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

## Реализация и проверка

- Для регрессии воспроизведи исходное поведение и проверь наблюдаемый результат. Для файловых операций и обновлений учитывай данные предыдущих версий, отмену, повторный запуск и частичный сбой.
- Запусти целевые тесты и затем `dotnet test RustText.slnx` из корня на Windows x64. При изменении поставки запусти Native AOT по [README](../README.md#запуск-и-сборка) и скопируй EXE в пустой каталог для ручной проверки. Папка публикации должна содержать один `rusttext.exe`.
- Тестируй окно с временным профилем `RUSTTEXT_PROFILE_DIR` и копиями файлов. Для фоновых проверок используй отдельный неактивный рабочий стол. Фикстуры и сценарии описаны в [отчёте о проверках](verification.md). При проверке обновлений используй временную копию установки и тестовый ZIP с контрольной суммой.

Для пакета обновления создай ZIP из одного опубликованного EXE и запиши рядом его SHA-256. Пример из корня worktree.

~~~powershell
$exe = 'src/RustText/bin/Release/net11.0/win-x64/publish/rusttext.exe'
$zip = 'target/RustText.NET-win-x64.zip'
New-Item -ItemType Directory -Path target -Force | Out-Null
Compress-Archive -LiteralPath $exe -DestinationPath $zip -Force
$hash = (Get-FileHash -LiteralPath $zip -Algorithm SHA256).Hash.ToLowerInvariant()
"$hash  RustText.NET-win-x64.zip" | Set-Content -LiteralPath "$zip.sha256" -Encoding ascii
~~~

## Коммит, push и проверка на GitHub

1. Проверь `git diff --check`. Добавь только файлы задачи через `git add -- <файлы>`. Проверь `git diff --cached --check` и прочитай `git diff --cached` целиком. Убедись, что в коммит попадают нужные новые файлы и что нет токенов, профилей, пользовательских логов или сборочных артефактов.
2. Сделай коммит, который можно понять по сообщению и проверить отдельно. Если владелец поручил оставить работу локально, заверши её после локального коммита и проверок. Перед push сверь адрес `origin`, имя ветки и `git log --oneline origin/main..HEAD`. Публикуй свою ветку обычным push:

~~~powershell
$branch = git branch --show-current
if ($LASTEXITCODE -ne 0 -or $branch -notlike 'codex/*') {
    throw 'Нужна рабочая ветка codex/*'
}
git push --set-upstream origin "HEAD:refs/heads/$branch"
if ($LASTEXITCODE -ne 0) {
    throw 'GitHub не принял push'
}
$head = git rev-parse HEAD
$published = git ls-remote --exit-code origin "refs/heads/$branch"
if ($LASTEXITCODE -ne 0 -or ($published -split '\s+')[0] -ne $head) {
    throw 'GitHub не подтвердил ожидаемый коммит'
}
~~~

При отказе non-fast-forward посмотри, кто и что добавил в ветку. Согласуй чужие изменения перед обновлением своей работы. Прямой push в `main` и перезапись опубликованной истории исключены из обычного процесса. [Git push](https://git-scm.com/docs/git-push)

3. После подтверждения SHA открой PR из рабочей ветки в `main` или обнови существующий PR этой ветки. Для незавершённого изменения используй черновик. Заполни [шаблон PR](../.github/pull_request_template.md). Для GitHub CLI сохрани готовое описание в файл. Например, для issue #17 выполни `gh pr create --base main --head $branch --title "Исправить проверку JSON (#17)" --body-file <файл>`. Без GitHub CLI используй подключение к GitHub или страницу сравнения веток. После публикации сверь номера в заголовке с issues, которые решает PR. [GitHub CLI](https://cli.github.com/manual/gh_pr_create)
4. Дождись проверок через `gh pr checks --watch` или [GitHub Actions](https://github.com/Illson/RustText/actions). Проверь, что результаты относятся к текущему коммиту PR. Ошибку разбери по логу и исправь в этой же ветке. При недоступности GitHub или внешнего окружения укажи конкретный блокер. [Проверки PR](https://cli.github.com/manual/gh_pr_checks)
5. Оставь worktree доступным, пока задача открыта или нужна для проверки. Когда он больше не нужен, проверь чистоту дерева и сохранность коммитов. Для worktree в Codex используй архивирование, для обычного Git — `git worktree remove <путь>` из другого checkout.

## Временные артефакты

1. До запуска сборки или проверки создай отдельную временную папку задачи с уникальным именем. Направляй туда синтетические логи и их копии, тестовые профили с черновиками, дампы, результаты тестов и промежуточные публикации. Готовые ZIP и другие файлы, которые получит пользователь, сохраняй по отдельному пути.
2. Для многогигабайтных замеров заранее оцени пиковый расход места, включая копии, дампы и параллельные прогоны. Начни с небольшой фикстуры. Создавай большую, если размер нужен для критерия проверки, и используй её повторно в рамках замера. Запиши параметры генерации и результаты в отчёт, чтобы фикстуру можно было воспроизвести.
3. По завершении прогона, включая сбой или отмену, останови запущенные для проверки процессы, сохрани нужные результаты и удали созданные задачей временные файлы. В скриптах, которые управляют всем прогоном, делай это в `finally`. Перед рекурсивным удалением сверь абсолютный путь с папкой задачи и проверь, что путь и его содержимое не перенаправляют через junction или символическую ссылку. Если файл занят, укажи его путь и причину в отчёте.
4. При завершении задачи проверь, какие крупные файлы ещё остались в worktree и папке артефактов. Удали ненужные промежуточные сборки и распаковки, когда они больше не требуются для повторной проверки. Сохрани выданные сборки, пользовательские данные и кэш, который ещё нужен для работы. Если worktree задачи больше не нужен, сначала проверь публикацию коммитов и доступность выданных файлов, затем архивируй его по [порядку завершения задачи](#коммит-push-и-проверка-на-github).

## Ревью PR

1. Сверь базовую ветку, текущий SHA и статус PR на GitHub. Для черновика выясни по описанию и обсуждениям, какая работа осталась. Прочитай цель, связанные issues, критерии и проверки. Посмотри весь diff в контексте кода. Для `Closes #N` проверь, чем подтверждено полное выполнение issue. Если критерий остался открытым, попроси в ревью указать частичную связь.
2. Проверь, обсуждалась ли проблема в этом PR. Если тред уже есть, добавь туда новые данные. Для нового дефекта выбери строку или диапазон в `Files changed`. В заголовке укажи приоритет (например, `[P2]`) и предлагаемое действие. Ниже опиши условие и последствие. Приложи короткое воспроизведение, результат проверки или обоснование по коду. В [замечании из PR #7](https://github.com/Illson/RustText/pull/7#discussion_r4591377163) автор показал, при каких байтах поиск пропускает совпадение. Замечание без подходящей строки оставь в итоговом тексте ревью.
3. Перед публикацией сверь SHA PR. Если он изменился, проверь новый коммит. Отправь замечания одним GitHub Review с решением `Comment`, как в [ревью PR #7](https://github.com/Illson/RustText/pull/7#pullrequestreview-5927410950). В итоговом комментарии укажи проверенный SHA, охват, выполненные проверки и их результаты, существенные ограничения и замечания, которые мешают слиянию. Если замечаний нет, так и напиши. После отправки дай ссылку на опубликованное ревью. [Как отправить ревью на GitHub](https://docs.github.com/en/pull-requests/get-started/reviewing-pull-requests-quickstart)
4. Если дефект нужно исправить до слияния, опиши в ревью сценарий проверки исправления. После публикации переведи PR в черновик через `Convert to draft`, даже при успешном CI. Если замечаний нет или остались только необязательные улучшения, сохрани текущий статус. Для каждого PR проверь итоговый статус на GitHub и укажи его в отчёте рядом со ссылкой на ревью. Если GitHub отклонил смену статуса, сообщи причину.
5. Автор отвечает в исходном треде. Если исправил дефект, укажи SHA и результат проверки. Если замечание спорное, приведи сценарий или объясни принятое решение. При повторном ревью проверь исходный сценарий на новом SHA и сообщи результат в том же треде. Если PR перевели в черновик из-за ревью, верни его в `Ready for review`, когда устранены все блокирующие замечания, прошли проверки текущего коммита и выполнены остальные условия готовности автора. [Пример повторного ревью](https://github.com/Illson/RustText/pull/6#pullrequestreview-5927414922)

### Что проверять по характеру изменения

- **Сохранение файлов.** Проследи весь путь от Ctrl+S до записи на диск и снятия состояния «Сохранение…». Если добавлена работа с Проводником или сетью, проверь сохранение обычного локального файла при недоступном сетевом рабочем столе и возможность закрыть окно при зависшем вызове Проводника. Уточни, какие именно вызовы ограничивает тайм-аут. [Ревью #43](https://github.com/Illson/RustText/pull/43#pullrequestreview-5959255050)
- **История и отрисовка.** Проверь, какие поиски выполняются при вводе текста с закрытым меню. Для вложенных обходов укажи размеры обоих списков и измерь стоимость на длинной истории. При восстановлении сессии сравни пустой файл и недоступный файл с ранее известным числом строк. Для недоступного файла история должна сохранить последнее известное значение. [Ревью #42](https://github.com/Illson/RustText/pull/42#pullrequestreview-5959263447)
- **Фоновые проверки.** Повтори запрос для одной версии текста до и после завершения задачи. Убедись, что разбор выполнился один раз. Затем измени текст во время проверки и проверь, что редактор показывает результат для новой версии. [Ревью #41](https://github.com/Illson/RustText/pull/41#pullrequestreview-5959267606)
- **Совместимость и CI.** Сверь вывод CI и убедись, что он включает тест проекта, в котором добавлена регрессия. В ревью укажи, что проверил CI, что воспроизвёл ревьюер и что подтвердил автор или владелец на целевой версии Windows. [Ревью #40](https://github.com/Illson/RustText/pull/40#pullrequestreview-5959274309)

## Что обеспечивает CI

[Windows CI](../.github/workflows/windows-ci.yml) собирает решение, запускает тесты и публикует приложение через Native AOT на Windows x64. Проверка публикации требует один `rusttext.exe` с нативным заголовком x64. Версия SDK задана в [global.json](../global.json). Исходники прежней реализации хранятся в [архиве](../archive/README.md).

CI запускается при push в `main`, в ветки `codex/**` и для PR в `main`. У него есть разрешение `contents: read`, а версии actions закреплены по SHA. Правила защиты ветки и выпуск новой версии меняются отдельно.
