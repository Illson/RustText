# Парные замеры производительности RustText

Этот стенд переносит [методику NetText](https://github.com/TheVSAKeeper/NetText/blob/046ac8b9136a07aa53d0c6d57692795443fa54d1/docs/comparison-methodology.md) на сравнение двух Git-ревизий RustText. Он отдельно измеряет запуск настоящего окна и операции ядра. [Опубликованное сравнение NetText и RustText 2.4.0](https://github.com/TheVSAKeeper/NetText/blob/046ac8b9136a07aa53d0c6d57692795443fa54d1/docs/comparison.md) — исторический результат другого стенда, не замер текущей версии. Для повторения межпродуктового сравнения используйте закреплённую версию стенда NetText.

Последовательность сопоставимых локальных серий: [история производительности](performance-history.md).

## Запуск

Нужны Windows x64, Git, PowerShell 7.4+, SDK .NET 11 и инструменты Visual Studio C++ x64 с Windows SDK для Native AOT. Из корня репозитория:

```powershell
# Сначала проверить весь измерительный контракт на малых файлах.
pwsh -NoProfile -File tools/Measure-RustTextPerformance.ps1 -Smoke -Iterations 2

# Затем сравнить нужные ревизии на полных входах.
pwsh -NoProfile -File tools/Measure-RustTextPerformance.ps1 -BaselineRef v2.6.0 -CandidateRef HEAD

# Только ядро, без интерактивного рабочего стола; это же проверяет Windows CI.
pwsh -NoProfile -File tools/Measure-RustTextPerformance.ps1 -CoreOnly -Smoke -Iterations 2 -BaselineRef HEAD
```

- Для GUI используйте интерактивный сеанс Windows, для фоновой работы — отдельный неактивный рабочий стол. Не взаимодействуйте с измеряемыми окнами. Не меняйте рабочий стол, разрешение, режим питания или нагрузку системы в середине серии. Обе версии прогоняются последовательно.
- Для полного сценария нужно не менее 12 ГиБ свободного места на локальном диске; для smoke или `-CoreOnly` — не менее 1 ГиБ. `-Iterations` — чётное число, по умолчанию 6. Сборка и полный прогон могут занимать несколько минут. `-OrderSeed` задаёт воспроизводимое перемешивание GUI-сценариев; `-MemorySampleMs` задаёт возраст процесса для среза памяти (по умолчанию 2000 мс). Если файлы не успевают открыться к срезу, увеличьте возраст и повторите серию с этим значением для обеих сборок.
- Стенд разрешает refs в полные SHA, экспортирует обе ревизии в отдельные каталоги и собирает Release Native AOT одним SDK. Незакоммиченные изменения приложения в замер не попадут. По умолчанию сравниваются `v2.4.0` и `HEAD`. Используйте только доверенные исходники: стенд запускает их сборку и EXE. Проверены структуры исходников 2.4.0 и 2.6.0; более ранние или реорганизованные ревизии могут требовать адаптера.
- `-OutputDirectory` задаёт **новый** каталог; иначе используется `target/performance/<id>/`. Фикстуры, временные профили и рабочие сборки удаляются после прогона, включая сбой. Остаток при ошибке очистки отмечается в `raw.json`.

## Окно

| Сценарий | Вход | Кэш DLL приложения |
| --- | --- | --- |
| `empty-cold` | Пустое окно | Пустой |
| `empty` | Пустое окно | Готовый |
| `text` | Обычный UTF-8, около 40 МиБ | Готовый |
| `json` | Массив JSON, около 10 МиБ | Готовый |
| `log` | Лог UTF-8, около 10 ГиБ, открыть в режиме лога | Готовый |

В smoke текст и JSON занимают около 64 КиБ каждый, лог — около 2 МиБ. Состояние кэша ОС не сбрасывается: cold относится только к кэшу графических DLL RustText. Для каждого запуска создаётся новый профиль с отключёнными обновлениями. В тёплом сценарии в него копируется кэш из прогрева той же версии; остальные данные прогрева не переносятся.

В каждом блоке порядок сценариев перемешивается; в чётных блоках первым идёт кандидат, в нечётных — база. Таймер начинается непосредственно перед `Process.Start`. Одна внешняя проба Windows фиксирует видимое окно заданного PID и первый успешный ответ на `WM_NULL`. Это показатели запуска окна и доступности оконного потока, не время полного открытия файла.

После первого ответа до среза памяти стенд подтверждает открытие файла. Заголовок должен совпасть, а `recent-files.json` в новом тестовом профиле — содержать полный путь и ожидаемый режим: запись с числом строк появляется после загрузки текста или JSON в редактор, а для лога нужна запись режима просмотра (не редактирования страниц) и маркер первого кадра. Время обнаружения сигнала `readyMs` включает запись истории и опрос, поэтому не используется как замер времени загрузки. Старый JSON без `guiReadiness` можно пересчитать, но он не подтверждает готовность документа.

Рабочий набор, его пик, private bytes и CPU снимаются при одинаковом заданном возрасте процесса; фактический возраст записывается. Пик — с начала процесса до среза, private bytes — не частный рабочий набор. Отклонение среза больше 100 мс, неверное открытие, тайм-аут или аварийный выход сохраняют ошибку и останавливают серию.

## Ядро

Обе копии горячих путей подключаются к одному процессу Native AOT через общий адаптер. Входы готовятся заранее: лог CRLF около 64 МиБ (2 МиБ для smoke), JSON и текст в памяти. Каждую версию прогревают, порядок в паре чередуют. Результат проверяется независимо от второй версии, за пределами таймера, в том числе при прогреве.

| Операция | Что проверяется |
| --- | --- |
| Индекс лога | Конечное смещение и число разделителей CRLF |
| Буквальный поиск (3 случая) | Промах, кириллическое совпадение у EOF, первые 32 частых совпадения |
| Regex (3 случая) | Промах с обязательным литералом, промах без литерала, совпадение у EOF без литерала |
| Форматирование JSON | Полный эталонный текст с отступом в два пробела и ожидаемыми переводами строк |
| Поиск в редакторе | Все диапазоны на ASCII-входе |
| Замена в редакторе | Число замен и весь выходной текст |

Поиск по логу сверяет байтовые смещения, позицию остановки и признак завершения. До переноса оптимизаций адаптер использует `ReadPage` и одну проверку regex на строку; новые ревизии запускают тот же потоковый алгоритм, что и «Найти», включая подготовку превью и контрольной суммы найденной строки. Запросы в фикстуре дают не более одного совпадения на строку, поэтому проверяемый результат одинаковый. Замер не включает окно, навигацию и фоновую индексацию. Форматирование и замена работают со строками, без отрисовки и применения к вкладке. Аллокации учитывают только управляемую память текущего потока.

## Результаты

`raw.json` содержит SHA ревизий, хеши стенда, EXE и входов, сведения о Windows/SDK/CPU/RAM/GPU/дисках, фактический порядок и все принятые наблюдения. Отдельные попытки GUI (включая прогрев и сбои) остаются в `gui/`; аргументы, вывод и коды завершения сборок и прогона ядра — в `logs/`. Перед публикацией сырых данных проверьте сведения об оборудовании и локальные пути в логах.

Отчёт показывает медиану и диапазон наблюдений, а также медиану и диапазон **отношений внутри пар** (`кандидат / база`, не отношение медиан). Если у базы есть нулевое значение, отношение не выводится. Небольшое число пар не позволяет оценить хвостовые задержки или гарантировать такой же результат на другой машине. Smoke и замеры с общего CI-раннера не используются для оценки производительности; CI проверяет воспроизводимость сценариев и отчёта без порогов времени.

Пересборка отчёта из завершённого прогона без запуска приложения:

```powershell
$run = 'target/performance/my-run' # подставьте каталог завершённого прогона
pwsh -NoProfile -File tools/Measure-RustTextPerformance.ps1 -RenderFromRawJson `
  -RawJsonPath "$run/raw.json" -ReportPath "$run/reproduced.md"
```

Поведенческие регрессии проверяются отдельно: см. [автотесты и ручные сценарии](verification.md).

### Добавить серию в историю

1. Возьмите предыдущий замеренный релиз или коммит за базу и прогоните обе ревизии заново на одной машине. Для сопоставления запишите версии стенда и SDK, хеши фикстур, размер входов и параметры прогона. Не сравнивайте медианы из независимых серий как парный результат.
2. Добавьте запись в [историю](performance-history.md) и приложите очищенный JSON в `docs/performance-runs/`. Сохраните измерения, SHA и хеши; уберите stdout/stderr, локальные пути и сведения об оборудовании, не нужные для сопоставления (например модели дисков). Логи сборки, профили, EXE и входные файлы не публикуйте.
3. Отмечайте сигнал регрессии, если в серии из шести и более пар все пары стали хуже, медиана парного отношения выросла не менее чем на 10%, а абсолютная разница значима для сценария. Ориентиры: 1 мс для времени, 1 МиБ для памяти процесса, 64 КиБ для управляемых выделений. При пересечении диапазона пар с `1,0` запишите, что направление эффекта не определено. Перед блокировкой выпуска повторите подозрительный сценарий независимо.

### Проверка изменений стенда

1. Запустите smoke с двумя парами. Ожидаются 20 срезов GUI плюс два отдельных прогрева, 40 замеров ядра и `status: complete`.
2. Повторно соберите Markdown из `raw.json` в том же каталоге. Он должен побайтно совпасть с исходным отчётом; каталог `work/` не должен остаться.
3. Проверьте, что нечётное число повторов и существующий каталог вывода отклоняются. Если наблюдение не укладывается в контракт, ищите причину в `gui/` или `logs/`, а не исключайте неудачный повтор из отчёта.
4. Отрицательные проверки GUI: окно с правильным заголовком, но без записи загрузки ожидаемого пути не проходит; лог, открытый в постраничном редакторе, не проходит даже при наличии маркера первого кадра.
