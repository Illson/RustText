# RustText — инструкции для агентов

RustText — редактор и просмотрщик больших логов для Windows x64 на Rust и GPUI Kit. Сборка, проверки и выпуск описаны в [README.md](README.md). Полный рабочий цикл — в [docs/development.md](docs/development.md).

## Рабочий цикл

- Выполняй каждую задачу с изменениями в отдельном Git worktree и ветке `codex/<задача>`. Новую задачу начинай от актуальной `origin/main`. Для продолжения той же задачи используй её ветку и worktree. В Codex worktree может начинаться с detached HEAD. Создай ветку до первого коммита.
- Перед правками сверь корень, ветку, `git status`, diff и цель задачи. Основной checkout и чужие worktree используй только для чтения. Сохраняй чужие правки.
- Перед правками проверь открытые issues и PR по теме. Если берёшь issue в работу, укажи, за какую часть отвечаешь. См. [правила связи PR с issues](docs/development.md#связь-pr-с-issues).
- При создании или обновлении PR по issue всегда добавляй её номер в конец заголовка, например `Исправить проверку JSON (#17)`. Если PR решает несколько issues, перечисли все их номера в скобках, например `(#18, #19)`. Это правило действует и для черновиков.
- Для сложной задачи зафиксируй критерии приёмки, риски и короткий план в issue, PR или документации задачи. Обычные технические решения принимай самостоятельно. Уточняй изменения, которые затрагивают данные пользователя, публичные контракты или выпуск.
- Делай небольшие проверяемые изменения. При исправлении ошибки добавляй регрессионный тест, когда сценарий воспроизводим. Для изменений поведения сначала запусти целевые тесты, затем Rust-проверки из README. Для изменений окна и работы с файлами применяй актуальные сценарии из [docs/verification.md](docs/verification.md) на отдельном тестовом профиле и копиях файлов.
- Перед коммитом проверь весь свой diff и `git diff --cached --check`. Добавь в индекс конкретные файлы задачи, сделай коммит с понятным сообщением и запушь рабочую ветку в `origin`. Проверь на GitHub, что опубликован нужный SHA. Если пользователь попросил оставить работу локально, соблюдай этот режим.
- После подтверждения SHA открой PR из рабочей ветки в `main` или обнови существующий PR той же задачи. Заполни [шаблон PR](.github/pull_request_template.md). Укажи `Closes #N`, если все критерии issue выполнены и проверены. Для частичной или смежной работы используй `Связано с #N`. Дождись результата GitHub Actions для текущего коммита PR. Исправляй ошибки в рамках задачи и повторяй проверки. Слияние, теги и выпуск выполняй по отдельной просьбе пользователя.
- При сбое публикации сохрани локальный коммит и сообщи точную причину. В итоговом отчёте укажи worktree, ветку, SHA, ссылку на опубликованный результат и фактический статус проверок.

## Временные артефакты

- Храни синтетические логи, тестовые профили, дампы и промежуточные сборки в папке своей задачи. Перед многогигабайтным прогоном оцени место на диске с учётом всех копий.
- После проверки, в том числе при сбое, убирай созданные задачей временные файлы. Перед итоговым ответом проверь остатки и сохрани выданные сборки, пользовательские данные и нужный кэш. [Порядок уборки](docs/development.md#временные-артефакты)

## Ревью PR

Если тебе поручено ревью, опубликуй GitHub Review по текущему SHA PR. Новые замечания привязывай к строкам diff, а результат проверки исправления сообщай в исходном треде. Если дефект нужно исправить до слияния, переведи PR в черновик на GitHub. В отчёте укажи охват, результаты проверок и подтверждённый статус PR. При просьбе ограничиться локальным отчётом опиши в нём замечания и рекомендуемый статус. [Порядок ревью и повторной проверки](docs/development.md#ревью-pr)

## Где искать код и контекст

- `src/workspace/` отвечает за окно, вкладки и координацию редактора. `src/session.rs`, `src/recent_files.rs` и `src/single_instance.rs` отвечают за локальное состояние и повторный запуск.
- `src/log_viewer/` и `src/log_io/` обслуживают большие логи. `src/log_trim.rs` выполняет физическую обрезку. Сохраняй обработку отмены, ротации и ошибок записи, а для изменения производительности приводи сопоставимые замеры.
- `src/updater/` отвечает за проверку и установку выпусков. Сохраняй проверку архива, восстановление при сбое и совместимость с именами файлов релиза из README.
- `tests/unit/` содержит тесты по модулям. Изменения формата файлов и сессии проверяй на существующих данных, ошибки ввода и частичную запись проверяй на временных файлах.
- Клади проверяемые знания рядом с кодом. Обновляй README при изменении интерфейса или команд, а результаты новых измерений записывай в документацию проверки. Повторяющуюся ошибку агента по возможности закрывай тестом или проверкой CI.
